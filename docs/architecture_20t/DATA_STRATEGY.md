# Jupiter Shot — Data Strategy

> **Status:** Reference design — not yet implemented.

---

## 1. Corpus Philosophy

The training corpus for Jupiter Shot is built on three principles:

**Principle 1 — License clarity.** Every dataset in the corpus must have a clearly documented license that permits use for training commercial AI models. Datasets with ambiguous licenses (e.g., "research only") are excluded. This is not a legal opinion; it is a risk management decision.

**Principle 2 — Quality over quantity.** A smaller, higher-quality corpus produces better models than a larger, noisier corpus at equivalent compute. The data pipeline invests heavily in quality filtering, deduplication, and domain-appropriate preprocessing.

**Principle 3 — Sovereign data for sovereign models.** For jurisdiction-specific deployments, the training corpus must include high-quality data in the target language(s) and domain(s). Generic English-centric corpora produce models that underperform on jurisdiction-specific tasks.

## 2. Approved Dataset Registry

The dataset registry (`training/dataset_registry.py`) maintains the authoritative list of approved datasets. The following datasets are approved for Stage 1:

| Dataset | Tokens (est.) | License | Source |
|---------|--------------|---------|--------|
| The Pile (filtered subset) | ~200B | Mixed (see note) | EleutherAI |
| Wikipedia (English) | ~4B | CC-BY-SA 4.0 | Wikimedia |
| GitHub Code (MIT/Apache/BSD) | ~100B | MIT/Apache/BSD | GitHub |
| ArXiv (CS, Math, Physics) | ~30B | CC-BY 4.0 | arXiv.org |
| PubMed Central (open access) | ~20B | CC-BY 4.0 | NIH |

**Note on The Pile:** The Pile contains subsets with varying licenses. The approved subset excludes Books3 (copyright disputed), DM Mathematics (license unclear), and any subset not explicitly permitting commercial use. The `DatasetSpec` for The Pile in `dataset_registry.py` specifies the approved subset configuration.

## 3. Data Quality Pipeline

### 3.1 Stage 1 Pipeline (Current)

The Stage 1 pipeline (`training/data_loader.py`) implements:

1. **Language detection**: fastText-based, filter to English (or target language)
2. **Length filtering**: Remove documents < 100 tokens or > 100,000 tokens
3. **Quality scoring**: Perplexity-based filtering using a small reference model (GPT-2)
4. **Exact deduplication**: SHA-256 hash-based, remove exact duplicates
5. **Basic toxicity filtering**: Keyword-based blocklist

### 3.2 Stage 2+ Pipeline (Planned)

For Stage 2 and beyond, the pipeline adds:

1. **Near-deduplication**: MinHash LSH (scaffolded in `training/deduplication.py`, `NearDuplicateDetector`)
2. **Quality classifier**: Trained on human-rated quality judgments
3. **PII detection**: NER-based, redact or remove personal information
4. **Domain classification**: Route to domain-specific quality thresholds
5. **Synthetic data integration**: Reasoning traces generated by smaller models

### 3.3 Near-Deduplication Status

The `NearDuplicateDetector` class in `training/deduplication.py` is currently a scaffold. It raises `NotImplementedError` for the `deduplicate()` method. Full implementation requires:
- MinHash computation (datasketch library, already in requirements)
- LSH index construction and querying
- Cluster identification and representative selection

This is planned for Stage 2. Stage 1 uses exact deduplication only.

## 4. Multilingual Strategy

The Stage 1 corpus is English-only. For sovereign deployments targeting non-English jurisdictions, the corpus must be extended with high-quality data in the target language(s).

**Arabic (target for Gulf region deployments):**
- Arabic Wikipedia: ~1B tokens (CC-BY-SA)
- Arabic news corpora: ~10B tokens (license varies, requires curation)
- Arabic legal/regulatory texts: ~2B tokens (public domain)
- Arabic social media: excluded (quality and license concerns)

**Note:** The GPT-NeoX-20B tokenizer has limited Arabic coverage (Arabic text is tokenized at the character level in many cases, resulting in very long token sequences). A jurisdiction-specific deployment targeting Arabic should evaluate whether a custom tokenizer with Arabic-optimized vocabulary is required. This decision must be made before Stage 2, as the tokenizer cannot be changed after training begins without invalidating all prior checkpoints.

## 5. Synthetic Data

Synthetic data (model-generated training examples) is planned for Stage 4 and beyond. The strategy is:

1. Use Stage 3 (200B) model to generate reasoning traces for math and code problems
2. Filter generated traces using a verifier (symbolic math solver, code execution)
3. Include verified traces in Stage 4 training corpus

This approach (similar to DeepSeek-R1 and Qwen-Math) has been shown to significantly improve reasoning benchmark performance. The quality of synthetic data depends critically on the quality of the generating model, which is why it is not used until Stage 3.
